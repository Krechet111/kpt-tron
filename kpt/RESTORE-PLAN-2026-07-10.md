# План восстановления БД TRON-ноды и доработки вотчдога

**Дата:** 2026-07-10
**Причина:** БД ноды на 186.246.12.181 повреждена жёсткими ресетами сервера ночью 10.07
(01:31 и 02:34). Нода застряла на блоке 84 322 078 с ошибкой `Tapos failed, different
block hash` — блок 84 322 079 из сети навсегда отвергается. Рестарты JVM не помогают,
повреждение на диске.

## Исходные данные (проверено)

| Что | Значение |
|---|---|
| Новый сервер | bisq@186.246.12.181, диск 154G, свободно 53G, повреждённая БД 98G |
| Старый сервер | bisq@89.23.100.234, доступ по ключу с моей машины — **работает** |
| Бэкап | `/home/bisq/kpt/kpt-tron-db-backup/output-directory/` — 91G, от 7–8 июля, та же lite-линия (`split_block_num=84057379`, совпадает с текущей нодой) |
| Связность серверов | порт 22 старого сервера доступен с нового — прямой rsync возможен |
| Sudo на новом | bisq: NOPASSWD на `systemctl start/stop/restart/status kpt-tron` |
| Вотчдог | скрипт `/home/bisq/kpt/kpt-tron/deploy/kpt-tron-watchdog.sh` принадлежит bisq (правится без root), запускается root'ом по таймеру каждые 2 мин; при остановленном сервисе ничего не делает — таймер на время работ трогать не нужно |
| Telegram-креды | `/home/bisq/.config/tron-telegram.env` (TG_BOT_TOKEN, TG_CHAT_ID) — root-вотчдог сможет их читать |

## Ручные действия с вашей стороны

**Не требуются.** Ключевой доступ есть к обоим серверам, все нужные root-операции
покрыты NOPASSWD-правилами sudoers, файлы скриптов и конфиг принадлежат bisq.

Исключение (маловероятно): если прямой rsync между серверами упрётся в запрет
по ключам/файрволу на уровне sshd старого сервера — понадобится либо ваш пароль,
либо перенос через мою машину (медленнее, но тоже без вашего участия).

## Этап 1. Остановка ноды и подготовка

1. `sudo systemctl stop kpt-tron` на новом сервере (NOPASSWD).
   Вотчдог при неактивном сервисе выходит без действий — мешать не будет.
2. Сгенерировать на новом сервере ed25519-ключ **без passphrase**, добавить его
   публичную часть в `authorized_keys` старого сервера (у меня есть туда доступ).
   Ключ временный — удалю на этапе 5.

## Этап 2. Перенос БД (91 ГБ)

1. **Удалить повреждённую БД** `output-directory/database` на новом сервере (98G).
   ⚠️ Без этого не хватит места (свободно 53G, нужен 91G). Отката не будет, но
   текущая БД бесполезна (нода никогда не уйдёт дальше 84 322 078). Страховка —
   нетронутый бэкап на старом сервере, источник открывается только на чтение.
2. Запустить на новом сервере фоновый rsync (nohup, лог в файл):
   `rsync -a --partial --info=progress2 bisq@89.23.100.234:/home/bisq/kpt/kpt-tron-db-backup/output-directory/ /home/bisq/kpt/kpt-tron/output-directory/`
3. Мониторить прогресс. 91 ГБ — ориентировочно 2–8 часов в зависимости от канала.
   При обрыве — перезапуск rsync докачает (`--partial`).

## Этап 3. Запуск и синхронизация

1. `sudo systemctl start kpt-tron`.
2. Контроль по логу и API (порт 8091): нода должна подхватить БД с высоты бэкапа
   (~84.26–84.28M, снят 7–8 июля) и догонять сеть (~60–100 тыс. блоков).
3. Критерий успеха: высота растёт, ошибок `Tapos failed` по блокам нет,
   отставание от Mainnet → 0. Вотчдог снова в строю автоматически.

## Этап 4. db.sync = true (после полной синхронизации)

Только когда отставание ≈ 0:

1. В `config.conf` на сервере: `db.sync = false` → `db.sync = true`
   (fsync при записи — БД переживает жёсткие ресеты; запись медленнее,
   на слабом vCPU следим, чтобы нода продолжала держать темп сети).
2. То же изменение в конфиге в репозитории (чтобы деплой не откатил).
3. `sudo systemctl restart kpt-tron`, наблюдение ~30 мин: нода не отстаёт.

## Этап 5. Доработка вотчдога + уборка

1. В репозитории доработать `kpt/scripts/deploy/kpt-tron-watchdog.sh`:
   - в state-файл добавить счётчик рестартов без прогресса высоты;
   - прогресс высоты между рестартами → счётчик сбрасывается (текущее поведение);
   - **3 рестарта подряд без прогресса** → больше не рестартовать, отправить
     алерт в Telegram (креды из `/home/bisq/.config/tron-telegram.env`);
   - пока проблема не устранена — повторять алерт каждые 6 часов, не чаще;
   - ручной `systemctl restart/start` администратором сбрасывает счётчик.
2. Проверить синтаксис (`bash -n`) и прогнать dry-run с override `STATE_DIR`.
3. Задеплоить скрипт на сервер (файл bisq — root не нужен; unit-файлы не меняются,
   таймер подхватит новую версию на следующем тике).
4. Удалить временный SSH-ключ нового сервера из `authorized_keys` старого.
5. Закоммитить в репозиторий: план, правки вотчдога, db.sync в конфиге.

## Риски

- **Консистентность бэкапа**: предполагаю, что бэкап снимался с остановленной ноды
  при миграции 7–8 июля (каталог помечен Jul 8 12:04). Если нода при снятии работала,
  БД может быть так же неконсистентна — узнаем на этапе 3 по тем же Tapos-ошибкам.
  В этом случае запасной вариант — официальный lite-снапшот TRON (скачивание ~30–50 ГБ).
- **Невозвратное удаление текущей БД** — осознанно, текущая БД неработоспособна.
- **db.sync=true на слабом vCPU** — возможное отставание при пиках; если нода
  перестанет успевать, обсудим откат этой опции (компромисс: скорость vs живучесть).
